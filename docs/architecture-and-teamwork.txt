Freax CQA — структура проекта и передача задач команде

Текущее состояние
Бэкенд и фронтенд уже реализованы. Это один репозиторий и один Node.js-процесс,
который обслуживает JSON API и статические HTML/CSS/JavaScript-файлы интерфейса.
Папки backend/ и frontend/ не требуются для логического разделения.
Новых фреймворков или переноса файлов для параллельной работы не требуется.

Соответствие гайду
— Интерфейс HTML/CSS/JavaScript: src/web/.
— Настройка критериев, типов, шкал, весов, N/A и версий: конфигурация + API + UI.
— GET организаторов выполняется через src/datasets.js на сервере.
— RU/KZ/EN, исходные роли и timestamps: src/domain.js, контракт Conversation.
— Одна LLM-оценка dialog_facts → evaluations, затем проверка и расчёт кодом.
— Карточка, источники/проверенные участки, отдельный грубый флаг и история.
— Подача апелляции и рассмотрение — разные действия; оригинал AI сохраняется.
— Звонок имеет переход к записи; STT/TTS и анализ интонации не подключены.
— JSON-хранилище выбрано для локального прототипа; гайд не требует SQL или Python.
— Дальнейшая адаптация к Dynamics возможна через отдельный транспорт/адаптер UI.
  Реального Xrm-адаптера нет. Текущий сервер разрешает iframe только своего origin:
  для настоящего встраивания нужно отдельно согласовать origin CRM и политику CSP.
— Экспорт DEV/PROD: src/submission.js + scripts/export-results.mjs.

Кому какие файлы
Фронтенд-разработчик:
  src/web/index.html — структура экранов;
  src/web/style.css — оформление и адаптивность;
  src/web/app.js — состояние экрана, формы и вызовы API;
  src/web/evidence.js — источники, контекст и навигация.
  Работа: UX, список/карточка, показ прогресса и частичных результатов,
  удобство апелляции, редактор критериев и демонстрация за 5 минут.

Бэкенд-разработчик:
  src/server.js — HTTP API и раздача фронта;
  src/service.js — оценка, сохранение оригинала и решения по апелляциям;
  src/store.js — атомарное JSON-хранилище;
  src/batch.js — очередь, пауза, продолжение и попытки;
  src/datasets.js — импорт API организаторов;
  src/history.js — список и фильтрация;
  src/execution.js — конфигурация и версии запуска.
  Работа: надёжность API/хранения, диагностика, экспорт, запуск и поставка.

AI и бизнес-правила — согласовывать с координатором:
  src/ai/* — промпт, схема, факты, транспорт и провайдер;
  src/domain.js — валидация входов, критериев и доказательств;
  src/scoring.js — веса, N/A, округление;
  src/submission.js — официальный формат сдачи.
  Не менять правила 04/05/06 ради совпадения с предварительной AI-разметкой.
  Новый промпт/схема/справка требуют отдельной версии и нового прогона.

Общие контракты:
  contracts/cqa.schema.json — Conversation, Checklist, Evaluation и апелляция;
  contracts/submission.schema.json — официальный results.json;
  config/checklist*.json — начальные правила и уточнения организатора;
  tests/ — проверки расчёта, API, доказательств, очереди и выгрузки.
  Изменение поля API сначала согласовать и отразить в контракте/проверке.

Как запустить
Нужен Node.js 24+. Для приложения и тестов npm-зависимостей нет.
1. Скопировать .env.example в локальный .env и заполнить выбранный провайдер.
2. npm start — интерфейс на http://127.0.0.1:3000 .
3. npm test — автоматические проверки.
4. Загрузить DEV или настроить CQA_DATASET_URL на сервере.
5. В UI выбрать «Уточнения организатора» для действующей конфигурации v2.
Рабочая проверенная копия на компьютере координатора — http://127.0.0.1:3004 .

Для фронтенда без ключа и реального AI:
node tests/fixtures/ui/server.mjs
Это явно синтетическая изолированная среда на порту 3002, не рабочая AI-оценка.
Есть карточки, история, источники, пересмотр и частичные результаты.
Без ключа обычное приложение также позволяет импорт и редактирование чек-листа.

Фронт обращается к /api/... того же сервера. Отдельный dev-server не обязателен.
HTML/CSS/JS перечитываются при запросе; после их правки обычно достаточно обновить
страницу. Серверные модули и промпт загружаются при старте процесса: изменения
применяются после перезапуска, когда нет активных оценок.

API, с которым работает фронтенд
GET /api/status — настройки/версии сервиса, доступность локального DEV, активный run.
POST /api/import — JSON диалога/массива/ответа API → нормализованные conversations.
POST /api/datasets/import — {group_id} → набор через серверный GET.
POST /api/datasets/local-dev — {} → сохранённый DEV, если он есть локально.
GET /api/checklists — сохранённые версии.
POST /api/checklists/organizer-update — {} → отдельная версия с уточнениями.
POST /api/checklists — изменённый снимок текущей версии → новая версия.
POST /api/evaluations — {conversation, checklist_id, checklist_version} → Evaluation.
GET /api/evaluations — краткая история, фильтры view/gross_error/status/
  conversation_id/checklist_version/run_id. Это не полные Evaluation.
GET /api/evaluations/:id — полная карточка.
POST /api/evaluations/:id/appeals — {revision, criterion_id, comment}.
POST /api/evaluations/:id/resolve — {revision, appeal_id, action, reason, review}.
GET /api/runs — прогоны и прогресс.
POST /api/runs — {conversations, checklist_id, checklist_version, subset, concurrency}.
GET /api/runs/:id — прогресс и IDs попыток.
POST /api/runs/:id/pause — {}.
POST /api/runs/:id/resume — {retry_failed:false}; true явно повторяет сбои.
GET /api/runs/:id/submission — официальный JSON только завершённого полного набора.
POST передаёт Content-Type: application/json. Авторизации для локального демо нет.

Формат Evaluation для UI
  conversation.transcript[]: message_id, timestamp, speaker, text;
  checklist.criteria[]: текущие критерии, а не жёстко зашитые восемь карточек;
  ai_review.criteria[] / final_review.criteria[]: массивы решений;
  original_score / final_score: рассчитанные сервером итоги;
  ai_facts, ai_metadata, prompt_version, run_id, configuration_hash: происхождение;
  appeals[]: отдельные обращения и решения, оригинал AI не переписывается.
criteria_by_id — внутренний формат ответа LLM, не формат REST-карточки.

Частичные результаты
resolved + value='na' — применимое по настройкам N/A с объяснением.
unresolved + value=null — не хватает решающей информации; есть missing_information.
При неизвестном балльном критерии полный итог null, известные ответы сохраняются.
Фронтенд отображает это состояние, не подменяет нулём и не считает итог сам.
В официальном файле null означает только N/A: такой диалог экспортируется как error.

Остающиеся ограничения
Независимой человеческой разметки/официального GT нет. Разбор 14 расхождений —
аналитическое заключение ассистента, а не новая официальная разметка.
12 частичных результатов требуют предметных правил компании; в одном звонке
дополнительно неразборчиво представление оператора.
Формат сдачи фиксирует восемь кодов, тогда как UI допускает новые критерии:
при контрольной замене сохранить согласованные коды/типы либо получить уточнение.
Внешняя CRM-интеграция и распределённое многопроцессное хранилище не реализованы;
для локального демонстрационного прототипа это не требование текущего гайда.
