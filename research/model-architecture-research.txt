Freedom Broker CQA: модели, научные основания и архитектура оценки
Дата проверки источников: 7 ноября 2026. Часовой пояс: Asia/Qyzylorda.
Статус: исследование и план эксперимента; AI-инференс не запускался, модели не скачивались, победитель не выбран.

1. РЕКОМЕНДАЦИЯ ДЛЯ НАШЕГО СЛУЧАЯ

Начать с gpt-6-astra, reasoning_effort=high, строгого JSON Schema и одного вызова на весь чек-лист. Это первый измеряемый baseline, а не утверждение о лучшей модели. Основание выбора: документированные reasoning/структурированный вывод и минимальная интеграционная дистанция до существующего OpenAI-compatible адаптера. Затем на том же входе сравнить отдельный сбор фактов перед выставлением оценок. Независимый облачный кандидат — claude-fable-5-1; третий — gemini-4-argon. gpt-6.1-sol оставить резервом по цене и совместимости, не объявлять его независимым судьёй относительно Astra только из-за другого ID.

Пользователь уточнил: основной путь — все модели через API. CUDA на нашем компьютере, Kaggle и локальная загрузка весов для этого не нужны. Предшествующее предложение Kaggle учтено только в необязательном приложении; на подготовку GPU-сервера основной план не расходуется.

Главный риск сейчас — отсутствие независимой разметки и неразрешённые трактовки правил. Смена бренда модели не создаёт GT и не устраняет неясность «первого ответа», «с самого начала», защищённых действий и возможности завершить чат.

Подтверждено: API ID и документированные возможности/цены перечисленных моделей существуют в официальных источниках на дату проверки. Не подтверждено: доступ конкретного аккаунта, стабильная задержка, соблюдение нашего полного контракта в реальном вызове и точность на RU/KZ/EN CQA. Документация и общий leaderboard не заменяют такой эксперимент.
Источники: [Astra](https://developers.openai.com/api/docs/models/gpt-6-astra), [Fable](https://platform.claude.com/docs/en/models/fable-5-1/overview), [Argon](https://ai.google.dev/gemini-api/docs/models/gemini-4-argon).

2. ИСХОДНЫЕ ДАННЫЕ И ГРАНИЦЫ ИССЛЕДОВАНИЯ

DEV уже получен и проверен: 65 диалогов, RU35/KZ15/EN15, 60 чатов и пять звонков; все звонки RU. В API-ответе нет покритериальных оценок или итогового GT. Разбиение pilot20/holdout10 сохранено в research/dev-split-v1.json до чтения содержимого пилота. Исследовательские формы пустые; архивный DEV_gold_template.json также содержит 520 пустых findings. Ни один из них не используется как эталон.

Чек-лист и руководство — первичные материалы задания. Pasted text.txt прочитан как пересланный референс; он повторяет материалы и просьбу об исследовании, не подтверждает дополнительные официальные правила. checklist.official.json из baseline содержит интерпретации, разобранные в research/baseline-methodology-review.txt. Статус «official» в названии файла и непроверенная ссылка на organizer voice clarification не заменяют исходное подтверждение.

STT/TTS, интонацию и дикцию сейчас не добавляем. Работа ведётся по уже выданным транскриптам. Предметной базы брокера пока нет. Официальная функция близости к GT жюри не опубликована в предоставленных материалах. Все предложенные далее показатели — внутренние диагностические.

Цены ниже: USD за 1 млн токенов, Standard, без кэша/Batch/инструментов/налогов. Нужны вход и весь оплачиваемый выход, включая reasoning по правилам провайдера. Значения контекста не означают полезности передачи огромного контекста для наших коротких диалогов.

| Модель / точный API ID | Вход / выход | Документированные возможности | Роль в эксперименте |
|---|---:|---|---|
| OpenAI gpt-6-astra | 10 / 50 | Контекст 1 050 000; выход до 128K; reasoning; Structured Outputs; Chat Completions и Responses | Первый кандидат качества; начать с high, строгой схемы, без инструментов |
| OpenAI gpt-6.1-sol | 2 / 10 | Контекст 1 050 000; выход до 128K; reasoning; Structured Outputs | Резерв с меньшей ценой; сравнить позднее при необходимости, не считать подтверждённо равноточным |
| Anthropic claude-fable-5-1 | 10 / 50 | Контекст 1M; выход 128K; adaptive thinking всегда включён, default high; JSON Schema в Messages API | Независимая модельная семья для основного сравнения/проверяющего |
| Google gemini-4-argon | 2 / 10 до 30.11.2026; затем 4 / 20 | Stable ID; единый бюджет вход+выход 1 048 576; обычный синхронный выход до 65 536, long decode отдельно; thinking low/medium/high; schema output | Третий кандидат другой семьи; использовать платный Developer API и его тариф |

Названия моделей OpenAI отдельно проверены в каталоге API. На открытых страницах Astra/Sol в разделе snapshots указан соответствующий недатированный ID; датированный ID самостоятельно не конструируем. Фиксируем requested_model, returned_model, дату, конфигурацию и хэши. Если провайдер меняет серверную реализацию под тем же ID, это остаточное ограничение воспроизводимости.

Fable 5.1 документирован как активная модель для всех клиентов; это не restricted Mythos 5.1. Наличие модели в каталоге не проверяет наши квоты и доступ. У Fable важен режим хранения данных, описанный ниже. Для JSON использовать native Messages, а не предполагать, что любой Anthropic endpoint принимает OpenAI response_format.

Argon первоначально анонсировался поэтапно; актуальная модельная страница показывает Stable API ID. Тем не менее проверка доступа нашего проекта обязательна. Не смешивать тарифы Gemini Developer API с тарифами Google Cloud/региональных платформ.

Точные источники: [Astra](https://developers.openai.com/api/docs/models/gpt-6-astra), [Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol), [OpenAI pricing](https://developers.openai.com/api/docs/pricing), [Fable](https://platform.claude.com/docs/en/models/fable-5-1/overview), [Fable availability](https://platform.claude.com/docs/en/models/fable-5-1/whats-new-fable-5-1), [Gemini model](https://ai.google.dev/gemini-api/docs/models/gemini-4-argon), [Gemini pricing](https://ai.google.dev/gemini-api/docs/pricing).
Машиночитаемая таблица: research/model-candidates.json. Опубликованные модельные оценки не доказывают преимущество на нашем чек-листе или KZ.

4. JSON, REASONING И ПОВТОРЯЕМОСТЬ

OpenAI: reasoning_effort для Chat Completions, reasoning.effort для Responses. Astra и Sol не поддерживают none; Astra не поддерживает пользовательские temperature/top_p/logprobs, и для reasoning-моделей нельзя механически переносить старый запрос с temperature=0. Указать high явно. Chat Completions достаточно для нашего text-only вызова без tool calling; миграция всего приложения на agent framework/Responses ради этого не нужна. Строгая схема задаётся JSON Schema, не json_object. Refusal, incomplete и достижение лимита обрабатывать до доверия к результату.
[Reasoning](https://developers.openai.com/api/docs/guides/reasoning), [current guide](https://developers.openai.com/api/docs/guides/latest-model), [schema](https://developers.openai.com/api/docs/guides/structured-outputs).

Anthropic: thinking={type:adaptive}, output_config.effort=high; структурированный вывод через output_config.format. Не задавать temperature/top_p/top_k по старому шаблону: текущие модели отвергают неподдерживаемые значения. Forced tool use — плохой обход для Fable: новая версия его ограничивает; нужен документированный structured-output путь. Из ответа извлекать text-блок, отдельно проверять stop_reason и отказ/лимит. Нативные citations и строгий JSON имеют ограничения совместимости; наши message_id/quote передаются как обычные поля схемы, не как обязательная встроенная функция citations.
[Thinking](https://platform.claude.com/docs/en/build-with-claude/thinking), [structured output](https://platform.claude.com/docs/en/build-with-claude/structured-outputs), [Fable changes](https://platform.claude.com/docs/en/models/fable-5-1/whats-new-fable-5-1).

Google: фиксировать thinking level и выбранную API-поверхность. Gemini 4 игнорирует устаревшие sampling-контролы с предупреждением; их нужно убрать. Уровни reasoning разных провайдеров не эквивалентны по вычислениям. Schema output документирован; возможны и native, и compatibility поверхности, но payload, ограничения схемы, stop/usage нужно проверять отдельно. Документация Argon рекомендует более длинные клиентские timeout для long decode; текущее приложение по умолчанию ждёт 120 секунд и ограничивает настройку 600 секундами. Это потенциальное узкое место, не повод обещать такую же скорость, как у другого API.
[Text generation](https://ai.google.dev/gemini-api/docs/text-generation), [thinking](https://ai.google.dev/gemini-api/docs/generate-content/thinking), [schema](https://ai.google.dev/gemini-api/docs/structured-output), [compatibility](https://ai.google.dev/gemini-api/docs/openai), [current model guide](https://ai.google.dev/gemini-api/docs/generate-content/latest-model).

Строгий JSON гарантирует форму в пределах поддержанного подмножества схемы, а не истинность, корректный N/A, отсутствие смысловой инъекции или релевантность цитаты. Поле с допустимым «yes» может быть содержательно неверным. Порядок событий 03 и смысл 04 нельзя доказать одним JSON.parse. Локальная валидация обязательна при любом режиме.

Ни temperature=0, ни одинаковый промпт не дают гарантии идентичных облачных ответов. Проверять устойчивость повторными прогонами, хранить все результаты и стоимость, не выбирать лучший повтор по GT. Самооценка «confidence=0.95» — не измеренная вероятность. На 20 примерах особенно мало данных для калибровки редких N/A/08; маршрут проверяющего сначала задаётся явными причинами проверки, а не произвольным confidence threshold.

5. ОБРАБОТКА ДАННЫХ

OpenAI API: данные по умолчанию не используются для обучения, если клиент явно не включил передачу для этой цели. Но «не обучают» не равно «ничего не хранят»: таблица документации указывает abuse monitoring до 30 дней; Responses имеет отдельное состояние, по умолчанию сохраняемое. Для предложенного stateless пути использовать store=false там, где он поддержан, не включать историю/conversations/files без необходимости. ZDR/региональные условия зависят от организации и возможностей endpoint.
[Data controls](https://developers.openai.com/api/docs/guides/your-data).

Anthropic: документация не допускает использование сохранённых данных для обучения без явного разрешения. Fable 5.1 — Covered Model: требуется 30-дневное хранение, ZDR для неё недоступен без специального разрешения Anthropic. Даже если общий structured-output feature отмечен ZDR eligible, это не отменяет модельное исключение. Для строгого требования к отсутствию хранения Fable нельзя предлагать как автоматически подходящий вариант.
[Retention](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention).

Google: в Paid Services содержимое не используется для улучшения продуктов по опубликованным условиям; unpaid режим допускает использование содержимого и человеческую проверку и прямо не предназначен для чувствительной/конфиденциальной информации. Argon не имеет Free tier. Статус платного доступа зависит от проекта/billing, а не от того, что пользователь не заметил списание. Это не обещание нулевого хранения.
[Terms](https://ai.google.dev/gemini-api/terms), [pricing](https://ai.google.dev/gemini-api/docs/pricing).

Тексты DEV нельзя считать полностью обезличенными только из-за отдельных скрытых имён. Аудиоссылки содержат подписи; они не нужны судье и уже исключаются из запроса приложения. Не отправлять токены, audio_url, внутренние ключи или сами экспертные метки в промпт оцениваемой модели. conversation_id лучше оставить серверу, предоставляя модели стабильные message_id. Секреты — только на сервере; в браузер и журналы их не помещать. Это требования к организации эксперимента; загрузка транскриптов во внешние сервисы в данном исследовании не выполнялась.

6. ДЕСЯТЬ НАУЧНЫХ РАБОТ И ПРОВЕРЯЕМЫЕ ИДЕИ

Ниже именно первичные публикации. Числа из чужих задач не трактуются как ожидаемая точность нашего решения.

P1. G-Eval — Liu et al., EMNLP 2023.
https://aclanthology.org/2023.emnlp-main.153/
Измерялось согласование с людьми на генерации диалогов и суммаризации. GPT-4-вариант с пошаговыми критериями и заполнением формы получил Spearman 0.514 для суммаризации; это корреляция, не 51.4% accuracy. Работа также отмечает предпочтение машинного текста.
Перенос: проверять явное применение каждой ступени и короткое обоснование вместо свободной общей оценки. Ограничение: другие задачи/модели, нет нашего N/A/KZ. Вероятностно-взвешенный score оригинального метода не переносится напрямую: у Astra нет нужных logprobs, а наш чек-лист требует дискретных ступеней. Идея: A1 с явно структурированными наблюдениями перед решением против обычного заполнения полей.

P2. Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena — Zheng et al., NeurIPS 2023, arXiv v4 от 24.12.2023.
https://arxiv.org/abs/2306.05685v4
Изучались согласование с экспертными/крауд-предпочтениями и position/verbosity/self-enhancement bias. Сильные судьи достигали более 80% согласия на соответствующих наборах.
Перенос: скрыть имя генерирующей/проверяющей модели, не вознаграждать длинную вежливую консультацию при нерешённом вопросе. Ограничение: предпочтение между ответами не равно абсолютной правильности восьми оценок. Идея: диагностические пары с тем же содержанием и иной длиной объяснения; не использовать Arena как выбор победителя CQA.

P3. Prometheus — Kim et al., ICLR 2024, arXiv v2 от 09.03.2024.
https://arxiv.org/abs/2310.08491v2
13B-судья обучался на GPT-4-сгенерированных рубриках/ответах/feedback; изучались корреляции с людьми и GPT-4 при наличии рубрики и эталонного ответа. Сообщается Pearson 0.897 с людьми на 45 пользовательских рубриках.
Перенос: дать модели явные ступени и проверенные опорные материалы. Ограничение: синтетический обучающий сигнал, нужный reference answer и отсутствие доказательства применимости к нашему трёхъязычному N/A. Идея: few-shot из независимой согласованной разметки. Не брать Prometheus как готовый GT или автоматически лучший локальный судья.

P4. FineSurE — Song et al., ACL 2024.
https://aclanthology.org/2024.acl-long.51/
Проверялись faithfulness, completeness и conciseness суммаризации, включая более мелкие единицы вместо единой оценки текста; сравнивались открытые и закрытые LLM и другие метрики.
Перенос: для 04 составить список существенных клиентских вопросов и связать каждый с ответом/следующим шагом и источником. Ограничение: клиентские потребности не тождественны заранее выделенным key facts суммаризации, а «существенность» требует нашей рубрики. Идея: A2 evidence ledger; отдельно считать пропуски вопросов и неверные факты, сохраняя оригинальный текст при второй стадии.

P5. LLMBar — Zeng et al., ICLR 2024, arXiv v2 от 16.04.2024.
https://arxiv.org/abs/2310.07641v2
419 пар ручного отбора противопоставляют соблюдение инструкции привлекательным, но неправильным ответам; исследуются различия моделей/промптов.
Перенос: оценивать конкретное правило, а не общую убедительность и дружелюбие. Ограничение: pairwise instruction following отличается от нашей абсолютной оценки работы оператора. Идея: искусственные случаи «вежливо, но не решено», «грубо, но фактически верно», «бот поздоровался вместо оператора»; метки задаёт человек по чек-листу, а не второй LLM.

P6. Large Language Models Cannot Self-Correct Reasoning Yet — Huang et al., ICLR 2024, v2 от 14.03.2024.
https://arxiv.org/html/2310.01798v2
Изучались GSM8K, CommonSenseQA, HotpotQA и модели поколения 2023; без внешнего сигнала исправление собственного ответа не гарантировало улучшение, иногда ухудшало, а сравнение с oracle feedback вводило в заблуждение.
Перенос: не добавлять обязательное «перепроверь себя» как доказанное повышение точности. Ограничение: это не тест сегодняшних моделей и не CQA; нельзя объявлять любые современные проверки бесполезными. Идея: отдельно измерять исправленные и испорченные решения после ревизии, сравнивать с тем же числом независимых вызовов.

P7. How Reliable is Multilingual LLM-as-a-Judge? — Fu, Liu, 2025, arXiv v1 от 18.05.2025.
https://arxiv.org/abs/2505.12201v1
Пять моделей, пять задач, 25 языков; межъязыковая согласованность оставалась ограниченной, средняя Fleiss kappa около 0.3; изучались факторы и ансамбль.
Перенос: RU/KZ/EN отчёт по отдельности и проверка устойчивости к языку. Ограничение: агрегат разных задач не определяет результат на KZ CQA; ансамбль повышает согласованность, что само по себе ещё не правильность. Идея: оригинальный KZ против варианта с вспомогательным переводом и независимой проверкой носителя.

P8. Lower-Resource, Higher Scores — Zhou et al., 2026, arXiv v3 от 26.08.2026; ранняя версия имела другое название.
https://arxiv.org/html/2607.14480v3
Семантически параллельные примеры на 23 языках выявляют сдвиги абсолютных оценок; высокая pairwise accuracy может скрывать различия в принятии по общему порогу. Авторы изучают связь с ресурсностью языка, неопределённостью и code switching.
Перенос: не считать хороший общий рейтинг доказательством одинаковой строгости RU/KZ/EN; не принимать самооценку уверенности за вероятность. Ограничение: другие задачи/языки/модели, не установлен эффект для нашей четвёрки. Идея: параллельные диагностические случаи и абсолютные покритериальные ошибки, без самовольной языковой поправки к официальным баллам.

P9. RubricEval — Pan et al., 2026, arXiv v1 от 26.03.2026.
https://arxiv.org/html/2603.25133v1
3486 rubric-level примеров; отдельные вызовы на рубрику и обоснование сравниваются с одним проходом по чек-листу. На использованных моделях наблюдалось преимущество более мелкого разбиения.
Перенос: отдельно проверить трудные 03/04/07 вместо безусловных восьми вызовов. Ограничение: бинарные instruction-following рубрики; часть reference labels получена модельным арбитражем с ручной проверкой, трудные несогласованные случаи отфильтрованы. Нет доказательства такого же выигрыша для наших ступеней/N/A. Идея: после A1/A2 абляция только слабых критериев с тем же оригинальным контекстом.

P10. KazMMLU — Togmanov et al., ACL 2025.
https://aclanthology.org/2025.acl-long.701/
23 тысячи вручную проверенных вопросов, из них 10 969 KZ и 12 031 RU, по знаниям и контексту Казахстана; исследованные модели заметно различались и сохраняли пробелы.
Перенос: нужен носитель KZ и отдельное языковое покрытие. Ограничение: knowledge QA старых моделей не является тестом CQA, финансовой политики или сегодняшних API. Идея: отдельно помечать ошибки понимания языка, переноса смысла перевода и собственно применения рубрики; не объявлять «лучшей для казахского» модель по чужому MMLU.

Практический научный вывод: сильнее всего обоснована необходимость мелких проверяемых решений, независимой человеческой калибровки и анализа языковых/стилевых смещений. Гарантированного переноса какого-либо прироста на CQA ни одна из этих работ не даёт.

Это документированные возможности; «до 100% взаимодействий» означает охват, не точность относительно GT. Для нас применим паттерн формы и проверяемого доказательства. Заимствовать просмотр контекста рядом с оценкой; не добавлять STT, инфраструктуру хранения и новые аналитические разделы ради сходства с продуктом.

8. СРАВНЕНИЕ АРХИТЕКТУР

A1. Один сильный вызов на все восемь критериев.
Полный транскрипт, конфигурация и доступные проверенные справки; в ответе по каждому критерию — наблюдение, доказательство/проверенный участок, применимость и значение. Баллы считает код.
Плюсы: минимум ошибок передачи, один контекст, простое воспроизведение и интеграция. Риски: пропуск отдельного вопроса, смешение 04/06, взаимное влияние критериев. Это обязательный контроль для более сложных схем.

A2. Сначала факты/события, затем применение рубрики.
Первый вызов: клиентские запросы, подтверждения проверки личности, раскрытия/действия, ожидание, жалобы и окончания, с message_id. Не выставляет баллов и не решает спорные официальные определения. Второй: получает ledger И полный исходный транскрипт, проверяет ledger и применяет рубрику.
Плюсы: проще увидеть порядок событий и покрытие запросов. Риски: ошибочный факт становится якорем, выдуманное защищённое действие, лишняя стоимость. Не передавать второй стадии только выжимку: это создаёт необратимую потерю контекста. Проверка достоинства A2 — реальный прирост, а не более длинное объяснение.

Отдельные сложные критерии.
После пилота можно выделить 03, 04 и/или 07; остальные оценивать общим вызовом. Для 03 — хронология, для 04 — вопросы и фактические опоры, для 07 — контекст окончания. Обычно 2–4 вызова вместо 8. Разрешение N/A остаётся конфигурацией. Риски: несогласованные факты между судьями и увеличение ошибок при разбиении. RubricEval — основание для абляции, не обещание результата.

A3. Первичный судья + выборочный независимый проверяющий.
Маршрут по заранее заданным признакам: требуемая идентификация без подтверждения/спорный порядок, решающий продуктовый факт без источника, неоднозначный конец, потенциальное 08, технически неполная оценка. Признаки выбираются до просмотра holdout. Проверяющий сначала получает оригинал и рубрику без первого вердикта; затем сравниваются выводы и доказательства. Это снижает якорение, но не делает ошибки независимыми.
При согласии сохраняется исходная машинная оценка; при разногласии — фиксированный арбитраж либо human review, с сохранением всех версий. Отсутствие решения не заменять нулём/N/A. Измерить долю исправленных И испорченных исходно верных оценок. Самоуверенность модели не единственный триггер.

Полный ансамбль разных моделей.
Два судьи не образуют большинство; три одинаково ошибающихся не создают GT. Для бинарных/NA можно предварительно задать правило консенсуса; при разногласии по применимости нужен разбор. Для ступеней не усреднять произвольно: среднее 4 и 7 даёт недопустимое 5.5 по 06. Выбор/медиана может оставаться разрешённой ступенью, но её правильность нужно проверить. Дублирование всех вызовов не рекомендуется первым шагом.

Проверенные продуктовые материалы для 04.
Если справки короткие — передать их целиком с source_id, версией, датой актуальности и точными цитатами. Это проще и прозрачнее необязательной векторной БД. Когда корпус велик, retrieval должен отдельно проверяться на пропуск нужного правила и подстановку устаревшего источника. RAG не гарантирует истинность или полноту. Пока проверенных справок нет, корректность некоторых рекомендаций невозможно подтвердить; отсутствие справочника не означает ошибку оператора или автоматический 0.

Few-shot.
Использовать только независимо размеченные и согласованные примеры из разрешённой части DEV. Нельзя генерировать метки тем же судьёй и называть их человеческим калибровочным набором. Лучше несколько коротких примеров различий Нет/N/A и соседних ступеней, чем целые ответы по всем знакомым ID.
Основную матрицу провести zero-shot. Если остаётся время, зарегистрировать отдельную few-shot абляцию на пилоте, взяв 4–6 человеческих примеров из remainder35. После этого заморозить инструкцию; holdout не становится новым набором few-shot. Близкие сценарии в разных языках могут дать скрытую утечку даже при разных ID.

KZ + перевод.
Основная оценка — по оригиналу. Вспомогательный перевод добавлять только как отдельную абляцию: сохранить message_id/роли/время, передать и оригинал, и перевод, в доказательствах ссылаться на оригинальные цитаты. Перевод может потерять отрицание, смягчить грубость или изменить порядок/намерение. Качество перевода проверяет носитель. Эта схема добавляет вызов и источник ошибки; из multilingual papers не следует гарантированное улучшение. Не объединять её с основной матрицей до понимания источника ошибок.

9. РИСКИ ПО НАШЕМУ ЧЕК-ЛИСТУ

02: достаточно исходных сведений — конкретное условие N/A, а не награда за дополнительный вопрос. Граница начала после бота остаётся вопросом методики.
03: отдельно определить необходимость проверки, наличие подтверждения и порядок относительно раскрытия/действия. Запрос имени/номера не равен завершению идентификации; нельзя придумывать список защищённых операций.
04: разложить запросы; отличать полезный следующий шаг от обещания без основания. Спасибо клиента не доказывает правильность, отсутствие справки не доказывает ошибку.
06: понятность и последовательность отдельно от полноты. Переспрос может быть новым вопросом. Трёхминутный SLA исключён.
07: различать закрытие оператором, реальный обрыв и конец выгрузки. Одна последняя реплика клиента не устанавливает отсутствие возможности прощания.
08: только три указанных типа; автор реплики важен; частное платное предложение достаточно без согласия. Флаг не меняет число баллов.
ASR/языки: скрытое имя, дубли и обрывочные фразы не превращать в доказанный дефект оператора. Метаданные language и реальные смешанные реплики могут расходиться; смотреть оригинал.
Prompt injection: transcript/reference — данные, не system instructions. Не давать судье инструменты, переход по ссылкам из разговора или право менять правила. Удалить conversation_id из модельного ввода, но сохранить серверную связь с message_id. Строгая схема не предотвращает смысловую подмену на допустимые значения: нужны искусственные инъекционные и ID-permutation проверки.
Новый критерий должен применяться через конфигурацию, а не список зашитых номеров или исключение в промпте. Условия автора baseline не становятся официальными из-за копирования в config.

10. ЦЕНА, ВЫЗОВЫ И ЗАДЕРЖКА: РАСЧЁТ, НЕ ИЗМЕРЕНИЕ

Для сравнимого планирования принимаем:
A1: 6000 входных токенов; 2000 видимого ответа + 4000 reasoning = 6000 оплачиваемого выхода.
A2: extractor 6000 вход / 3000 выхода; grader 8000 вход / 6000 выхода. Итого 14 000 вход / 9000 выхода, два вызова.
Это модель токенов, не измерение нашего DEV. Токенизаторы, KZ и фактические reasoning-токены изменят расход. Справки и schema уже должны помещаться в предполагаемый вход; при другом размере пересчитать.

| Вариант | Вызовов на диалог | Astra / Fable | Sol / Argon по текущей цене |
|---|---:|---:|---:|
| A1 | 1 | 0.360 USD | 0.072 USD |
| A2 | 2 | 0.590 USD | 0.118 USD |

Формула: сумма по всем вызовам (input_tokens * input_rate + billed_output_tokens * output_rate) / 1e6. Reasoning не прибавлять второй раз, если он уже входит в оплачиваемый output. Кэш/повторы/ошибки/проверяющий/перевод — отдельные строки расхода, а не бесплатные детали. Неуспешный HTTP ответ/тайм-аут не доказывает отсутствие списания.

A3 для иллюстрации: Astra A1 0.360; независимый Fable reviewer 9000 вход / 4500 выхода = 0.315. Если проверяются q=30%, а у d=40% проверенных требуется ещё один арбитр той же расчётной цены, среднее 1+q+q*d=1.42 вызова и 0.4923 USD. Это допущения q/d, не ожидаемые частоты на реальных данных. Верхний случай — три вызова.

Задержка неизвестна. Для расписания можно заложить условные 30–180 секунд на облачный вызов: A1 30–180, A2 60–360, проверенный и арбитрируемый A3 до 90–540 секунд плюс очередь. Это инженерный резерв, не измеренный p50/p95 или обещание провайдера. При длинном reasoning диапазон может быть превышен. При необходимости длинного timeout нужен asynchronous job/polling; не скрытый повтор вызова и двойное списание.

Для основного пилота 3 модели × 2 архитектуры × 20 диалогов = 120 оценок и 180 API-вызовов:
Astra 19.00 USD; Fable 19.00; Argon 3.80; всего 41.80 при указанных токенах.
Два дополнительных повтора на пяти фиксированных случаях, по одной выбранной архитектуре на модель: если все A2, ещё 60 вызовов и 12.98 USD.
Один holdout10 для двух зафиксированных финалистов: 20 оценок, до 40 вызовов; если оба дорогие A2 — 11.80 USD.
Итого иллюстративно 66.58 USD без retry/cache/tools, до 280 вызовов. Не является разрешением расходов или согласованным бюджетом.

Контроль расхода важнее среднего: при лимите 32768 выходных токенов НА КАЖДЫЙ вызов, тех же входах и Standard тарифах потолок для пилота около 225.07 USD, повторов 75.17 и дорогого holdout 68.34, вместе около 368.57 до дополнительных попыток. Это грубый лимитный сценарий; вход тоже нужно ограничить, иначе абсолютного потолка нет. В отдельном запуске оператор задаёт лимит расходов и число попыток; при превышении — остановка с явным статусом. Никаких API-вызовов в рамках исследования не было.

11. МАЛЕНЬКИЙ ВОСПРОИЗВОДИМЫЙ ЭКСПЕРИМЕНТ

До содержательного прогона:
— выбрать и зафиксировать чек-лист, справки, хэши транскриптов и параметры;
— проверить доступ/контракт каждого API на искусственном безопасном примере, без приписывания этому тесту точности;
— провести независимую blind разметку pilot20 экспертами A/B. Носитель KZ обязателен для разрешения языковых вопросов; предметный эксперт нужен для спорной правильности 04. Сохранить исходные разметки и adjudication. Не показывать экспертам AI-ответы до фиксации.
— неразрешённые случаи помечать отдельно, не выдумывать GT. Человеческий provisional reference всё ещё не официальный GT организаторов.

Основная матрица:
Модели: gpt-6-astra/high, claude-fable-5-1/adaptive high, gemini-4-argon/high.
Архитектуры: A1 и A2, без few-shot, перевода, автоматического ансамбля и изменения рубрики между клетками.
Входы: одни и те же pilot20, роли, message_id, оригинальные времена и один snapshot справок. Объяснение на одном языке, цитаты на языке оригинала.
Лимиты: явный output cap 32768 на вызов, поддерживаемые параметры, отсутствие инструментов и скрытого fallback. Для невоспроизводимого облачного ID сохранить returned model и дату. Повторять семантическое решение по ошибке запрещено без зарегистрированного протокола.
Пять случаев для повторов выбрать по зафиксированному правилу до просмотра результатов, с языковым покрытием; не выбирать только проигрыши любимой модели.
Порядок вызовов перемешать с зафиксированным seed, чтобы скорость/нагрузка/порядок просмотра меньше влияли на сравнение.

Оценка:
1) Exact accuracy по каждому критерию, N/A как отдельный класс, матрицы и числители/знаменатели.
2) Для 02/03/04/07 — ошибки применимости; для 08 — recall/precision и список пропущенных нарушений независимо от общего балла.
3) Для 04/06 — MAE только на числовых парах, рядом число пропусков/N/A-расхождений.
4) Итог — MAE/RMSE/bias и все пары; обязательны completion rate, доля полных восьми ответов и число доступных итогов. Отказ/timeout/unknown не исключать так, чтобы улучшить видимую точность.
5) Экспертный аудит релевантности доказательств; существование цитаты проверяется кодом, достаточность — человеком.
6) RU/KZ/EN и chat/call раздельно. Текущий comparator не имеет языковых срезов: присоединить метаданные по conversation_id отдельным read-only отчётом. Пять KZ в пилоте дают слабую статистику; не объявлять языкового победителя по одному случаю.
7) Стоимость всех вызовов, p50/p95 фактической задержки, повторяемость. Не использовать модель-судью для измерения собственной правильности вместо human reference.

Отбор: на пилоте выбрать не более двух полных pipeline-конфигураций. Не оптимизировать единственный скрытый сводный коэффициент: смотреть покритериальные ошибки, 08, MAE и покрытие. При сопоставимом качестве отдавать предпочтение меньшей сложности; точного «веса» этих факторов от жюри нет. Дополнительный A3/разбиение критериев/few-shot/перевод — по одному зарегистрированному пилотному изменению на обнаруженный тип ошибки, не бесконтрольный grid search.

После выбора заморозить весь pipeline и провести одно сравнение двух финалистов на holdout10; после просмотра меток не превращать его в тренировочный набор. Сохранить обе конфигурации/все результаты. Новые контрольные10 организаторов — отдельная внешняя проверка, они не заменяются нашим holdout.
Разные ID не гарантируют независимость: в DEV есть сходные multilingual сценарии. Для интервалов единица — диалог/семейство сценариев, не восемь коррелированных ответов. На 10 случаях разумнее показать все ошибки и неопределённость, чем доказательство «лучшей LLM».

Запуск сравнения уже реализован в research/compare_evaluations.py. По умолчанию это original AI, а не reviewed final после человека. Пустые/спорные value=null не превращаются в no/0/N/A. Модельные промежуточные оценки и последующее решение машинного pipeline нужно сохранить отдельно от human appeal.

12. МИНИМАЛЬНОЕ ВНЕДРЕНИЕ В NODE.JS

Текущий provider.js использует fetch и OpenAI-compatible Chat Completions, json_object, timeout, finish_reason и usage. domain.js валидирует допустимые значения и доказательства; scoring.js считает веса; service.js хранит исходное/пересмотренное. Сохраняем эту структуру.

Первый шаг — прямой Astra A1:
— capability-конфигурация модели/протокола, явные reasoning и output cap, строгая JSON Schema вместо одной гарантии json_object;
— отделить построение rubric prompt/schema от transport;
— неизвестные/неподдерживаемые параметры не отправлять «для единообразия»;
— тест на schema/refusal/truncation, затем ограниченный прогон при наличии меток и доступа.

Далее по одному native адаптеру:
OpenAI Chat/Responses — по выбранной поверхности, без forced tools.
Anthropic Messages — system/messages, output_config.format, content blocks, stop_reason и правильный заголовок версии по текущей документации.
Google — native или явно проверенная compatibility поверхность, собственная thinking/usage/finish обработка.
Все приводят результат к существующему Review и метаданным. Нет оснований добавлять LangChain/LangGraph/векторную БД только для маршрута из двух последовательных вызовов.

Для A2: внутренний EvidenceLedger с message_id, типом наблюдения, точной цитатой/диапазоном и ограничением проверки. Ledger — вспомогательное утверждение, не истина. После извлечения проверить ссылки кодом; grader снова видит оригинал.
Для A3: отдельная стратегия routing, независимая первая оценка reviewer, дифф и ограниченная политика арбитража. Триггеры/модели/промпты версионируются, промежуточные решения неизменяемы.

Схема вывода строится по config. Можно использовать объект с обязательными ключами критериев и отдельным enum value для каждого, затем нормализовать к Review.criteria[]; это снижает риск повтора ID/неправильной ступени. Условия существования всех ключей, допустимости N/A, ссылки и хронология всё равно проверяются кодом. Технический unresolved/error отдельно от официальных значений; текущий service может завершать такой run как failed, а не выдумывать баллы.

Метаданные на каждый вызов: experiment/run/evaluation ID, pipeline/prompt/schema version и hash, model requested/returned, provider endpoint family, reasoning settings, input/reference/checklist hashes, attempt/stage, start/end/duration, finish/refusal/error kind, input/output/reasoning/cache usage, расчётная/фактическая стоимость и источник цены. Не писать секреты, signed URL и приватные reasoning-тексты в журнал. Суммарная стоимость — сумма ВСЕХ попыток; неизвестный расход помечается unknown, не 0.

ai_review/original_score — исходный результат всего машинного pipeline до апелляции. Первый LLM-вызов внутри pipeline и арбитражные изменения — отдельные internal records; их не стирать. final_review/final_score остаются результатом human review. Так comparator не смешивает человеческую правку с точностью AI.

Приёмка до оценки качества:
— новый критерий из UI действительно входит в schema/prompt; хэш/версия меняются;
— значения вне ступеней, запрещённый N/A, несуществующие цитаты/дубли ID отклоняются;
— 03 не получает доказательства «до» из более поздней реплики;
— 08 меняет флаг, а не общий балл;
— исходная оценка сохраняется при апелляции;
— смена ID при том же тексте не подставляет готовую оценку, изменение текста/чек-листа инвалидирует кэш;
— отказ, обрезка, HTTP 429/5xx, тайм-аут и повтор не скрываются как успешная оценка;
— синтетическая инструкция внутри transcript не может менять конфигурацию/вызвать инструменты; смысловая устойчивость проверяется отдельными случаями;
— все расходы и pipeline version воспроизводимы в отчёте.
Это проверки механики, не доказательство совпадения с GT.

14. ЧТО ПОДТВЕРЖДЕНО, ЧТО НУЖНО ИЗМЕРИТЬ

Подтверждено первичными источниками: перечисленные API ID, опубликованные цены/контекст/параметры, schema-возможности и важные условия хранения; существование научных результатов и инженерных паттернов. Документы Google иногда возвращали text/markdown, который web parser не поддерживал: страницы прочитаны прямым GET, а не заменены поисковым сниппетом. Context7 использован после resolve-library-id для OpenAI/Claude/Gemini/llama.cpp/Kaggle/Promptfoo/Langfuse; API-концепты запрашивались отдельно.

Гипотезы: A2 лучше A1, reviewer исправляет больше ошибок, чем портит, большой reasoning лучше на наших ступенях, перевод помогает KZ, few-shot улучшает неизвестные сценарии. Любая из них может не подтвердиться. Ни одна модель не доказана лучшей для KZ или для общего CQA.

Для реального измерения нужны: независимые покритериальные метки и разбор разногласий; подтверждённая версия правил; проверенные предметные материалы для спорного 04 либо честные ограничения; доступ выбранных API и лимит расходов; право на передачу конкретных данных провайдеру. Часть этих условий может уже быть у команды, но в этом исследовании учётные записи и договоры не проверялись.
